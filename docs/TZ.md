# Разработка PrimeWalker-2: Комплексное Техническое Задание для Программы визуализации простых чисел с расширенным функционалом экспорта и персистентности состояния

## Общие Требования и Архитектурный Контекст

Настоящий документ представляет собой техническое задание (ТЗ) на разработку десктопного приложения PrimeWalker-2. Целью проекта является создание расширенной версии существующего инструмента для визуализации простых чисел, с акцентом на углубление математического анализа, улучшение пользовательского опыта (UX) через оптимизацию рендеринга и предоставление мощных аналитических возможностей <Research Goal><Conversation History>. Программа должна представлять собой автономное, офлайн-приложение, работающее на локальном компьютере пользователя, что подразумевает полную независимость от интернет-соединения для всех ключевых функций, включая генерацию, отрисовку и экспорт результатов <Research Goal>.

Основой для нового приложения служит существующий репозиторий `Bizonrelax/PrimeWalker-2`, который будет использован как основа для дальнейшей разработки [[39](https://github.com/bizon)]. Среда разработки и исполнения должна соответствовать той, что используется в другом репозитории пользователя, `Protfrg` [[39](https://github.com/bizon)], что предполагает использование современных технологий для создания кроссплатформенных десктопных приложений. На основе предоставленных контекстных данных и анализа лучших практик в области разработки программного обеспечения, рекомендуется использовать фреймворк Qt с его Python-оберткой PySide6 или PyQt6 [[99](https://wiki.qt.io/Handling_PDF), [102](https://www.pythonguis.com/faq/pyqt6-qsettings-how-to-use-qsettings/)]. Этот выбор обоснован наличием в Qt встроенного модуля `QtPrintSupport` для высококачественного вывода на принтер и форматирования PDF, а также класса `QSettings` для надежного хранения настроек пользователя между сессиями [[102](https://www.pythonguis.com/faq/pyqt6-qsettings-how-to-use-qsettings/), [103](https://contingencycoder.wordpress.com/2013/04/16/restoring-qt-application-state-and-geometry-part-1/)]. Кроме того, Qt предоставляет мощные инструменты для графического рендеринга (`QtGui`) и создания кросс-платформенного UI, что идеально соответствует требованиям проекта [[99](https://wiki.qt.io/Handling_PDF)].

Архитектура приложения должна быть спроектирована с учетом принципов разделения ответственности и модульности. Предлагается следующая трехуровневая структура:
1.  **UI Layer (Слой Интерфейса):** Отвечает за отображение данных и обработку пользовательского ввода. В рамках Qt это будет главный окно приложения (`QMainWindow`), содержащее виджеты, такие как `QSpinBox`, `QComboBox`, `QPushButton` и область для отрисовки (`QWidget` или `QGraphicsView`). Этот слой должен быть максимально легковесным и не содержать бизнес-логики. Для оформления интерфейса рекомендуется использовать библиотеку Qt-Material, которая позволяет создавать современные и темированные интерфейсы, включая возможность переключения между светлыми и темными темами в реальном времени [[106](https://qt-material.readthedocs.io/)].
2.  **Application Logic Layer (Слой Логики Приложения):** Это ядро программы. Он содержит классы для генерации последовательностей простых чисел (например, `PrimeGenerator`), классы для различных алгоритмов визуализации (например, `UlamSpiralVisualizer`, `JacobLadderVisualizer`), и менеджер состояния проекта (`ProjectManager`). Этот слой взаимодействует с данными и логикой, но не имеет прямого доступа к UI или файловой системе. Все коммуникации с другими слоями должны осуществляться через четко определенные интерфейсы (API). Для обмена сообщениями между компонентами можно использовать шаблон «наблюдатель» или легковесный механизм событий.
3.  **Data Persistence and External Services Layer (Слой Хранения Данных и Внешних Сервисов):** Этот слой отвечает за все операции, связанные с внешним миром: чтение и запись настроек пользователя (`QSettings`), сохранение и загрузка проектов (.pwalk файлов), управление историей экспорта и сбор глобальной статистики. Он также будет инкапсулировать логику экспорта в различные форматы, делегируя задачи рендеринга соответствующим сервисам. Для обеспечения отказоустойчивости и корректной работы в режиме офлайн-first, этот слой должен иметь стратегии для локального хранения данных (например, SQLite или сериализованные объекты в JSON/YAML) и синхронизации, если таковая потребуется в будущем [[18](https://developer.android.com/topic/architecture/data-layer/offline-first), [19](https://saiko.com.gr/en/offline-first-desktop-application/)].

Программа должна быть спроектирована с ориентацией на будущее развитие. Структура кода должна позволять легко добавлять новые алгоритмы визуализации путем создания новых классов, которые будут наследоваться от общего абстрактного базового класса `BaseVisualizer`. Аналогично, новые методы генерации простых чисел должны быть инкапсулированы в классах, реализующих общий интерфейс `PrimeGenerationStrategy`. Такой подход обеспечивает расширяемость и упрощает поддержку кодовой базы в долгосрочной перспективе. Все сохраняемые параметры, включая геометрию окна, настройки интерфейса и история экспортов, должны храниться в централизованном хранилище, например, в файле конфигурации, управляемом `QSettings`, чтобы избежать дублирования логики и обеспечить согласованность данных [[4](https://info.erdosmiller.com/blog/persistent-settings-in-desktop-applications), [102](https://www.pythonguis.com/faq/pyqt6-qsettings-how-to-use-qsettings/)].

Целевой пользователь — это исследователь, энтузиаст математики, студент или просто любопытный человек, интересующийся свойствами простых чисел. Поэтому интерфейс должен быть интуитивно понятным, а процесс генерации и экспорта — максимально автоматизированным, минимизируя необходимость в сложных настройках со стороны пользователя <Conversation History>. Например, при экспорте большого изображения система должна самостоятельно рассчитывать оптимальное количество плиток и их расположение, а также генерировать все необходимые монтажные метки, как это предлагают специализированные онлайн-сервисы [[20](https://www.pdf2go.com/print-poster), [26](https://oxygenpdf.com/tools/posterize-pdf)]. Программа должна работать на современных версиях Windows, macOS и Linux [[52](https://www.primeworkshub.com/desktop)]. Требования к аппаратному обеспечению должны быть минимальными, но достаточными для комфортной работы: процессор x86_64 совместимый, 8 ГБ оперативной памяти, 2 ГБ свободного места на диске [[50](https://docs.aws.amazon.com/quick/latest/userguide/getting-started-desktop.html)]. Однако следует предусмотреть механизмы для обработки сценариев, когда пользователь пытается сгенерировать изображение, которое значительно превышает возможности системы, например, путем ограничения максимального числа шагов или предоставления возможности отмены операции.

Весь код должен быть оформлен в соответствии с PEP 8 для Python, а документация должна быть включена в исходники для облегчения дальнейшей поддержки. Проект должен быть размещен в Git-репозитории с четкой структурой ветвления (например, `main` для стабильных выпусков, `develop` для текущей разработки и `feature/*` для отдельных нововведений).

## Функциональные Требования: Интерфейс Пользователя и Алгоритмы Визуализации

Функциональные требования этого раздела описывают детальное устройство пользовательского интерфейса (ПИ) и набор доступных алгоритмов для визуализации последовательностей простых чисел. Цель состоит в том, чтобы предоставить пользователю мощный, но интуитивно понятный инструмент для исследования и создания уникальных математических образов.

**Главное Окно Приложения**

Главное окно приложения должно быть простым, чистым и сфокусированным на основной задаче — генерации и отображении визуализации. Его элементы управления должны быть расположены в виде панели инструментов или диалогового окна на одной из сторон (например, справа или слева), оставляя центральную часть экрана свободной для самого рисунка. Все элементы управления должны быть реализованы с использованием стандартных виджетов Qt для обеспечения привычного внешнего вида и поведения на каждой платформе.

**Требования к компоновке главного окна (ревизия ТЗ 2, CHANGE-001)**

Компоновка окна обязана удовлетворять следующим проверяемым требованиям:

1. **Полная видимость без прокрутки при развёрнутом окне.** При развёрнутом на весь экран окне на типичном разрешении 1920×1080 все элементы управления (обе группы параметров и кнопки действий) должны быть видимы одновременно; вертикальная прокрутка панели не должна требоваться. Прокрутка допускается как аварийный режим только при сильно уменьшенном окне.
2. **Рисунком занят максимум площади.** Панель управления — фиксированной узкой ширины (около 320 пикселей), центральная область полностью отдана под рисунок и растягивается вместе с окном.
3. **Двухколоночная панель.** Внутри панели параметры размещаются компактно: поля «метка над полем» группируются в две колонки (логические группы сохраняются), что исключает длинный вертикальный список из одного столбца.
4. **Кнопки действий закреплены внизу панели** и остаются видимыми при любом размере окна.
5. **Строка состояния внизу окна** занимает всю ширину (под панелью и холстом), а не только центральную область.
6. **Размер окна по умолчанию** подбирается под полноэкранные разрешения (ширина не менее 1280, высота не менее 720); геометрия восстанавливается из сохранённых настроек.
7. **Масштабирование рисунка колесом мыши с зажатой Ctrl.** Колесо с Ctrl увеличивает или уменьшает изображение относительно точки под курсором (зум 10 % на щелчок колеса, диапазон от подгонки под окно до ~40×). **Алгоритмы Визуализации**

Приложение должно поддерживать несколько различных алгоритмов для преобразования последовательности чисел в двумерный или трехмерный рисунок. Это позволит пользователю исследовать различные аспекты распределения простых чисел.

1.  **Спираль Улама (Ulam Spiral):** Это наиболее известный и фундаментальный метод визуализации. Числа располагаются в спирали, начинающейся в центре сетки, и движущейся против часовой стрелки. Простые числа выделяются особенным цветом, что часто выявляет невероятно плотные диагональные линии, указывающие на связь простых чисел с определенными квадратичными полиномами, такими как $n^2 + n + 41$ [[105](https://www.complexity-explorables.org/explorables/prime-time/), [149](https://www.3blue1brown.com/lessons/prime-spirals/), [150](https://www.youtube.com/watch?v=dux1TBAmndM)]. Реализация должна учитывать ориентацию спирали (по умолчанию против часовой стрелки) и корректно обрабатывать четность размера сетки, что может требовать дополнительного поворота для обеспечения стабильности картины [[22](https://blogs.sas.com/content/iml/2014/01/27/ulam-spirals.html)].

2.  **Лестница Якова (Jacob's Ladder):** Этот алгоритм представляет последовательность чисел в виде пути, который движется вверх или вниз, меняя направление каждый раз, когда встречается простое число [[76](https://blog.computationalcomplexity.org/2025/06/the-distribution-of-prime-numbers.html), [151](https://www.mdpi.com/2297-8747/25/1/5)]. Например, если текущее направление "вверх", то при появлении простого числа направление меняется на "вниз", и наоборот. Это создает уникальные, волновые и "лестничные" паттерны, наглядно демонстрирующие "восстания" простых чисел в ряду натуральных.

3.  **Ход Простого Числа (Prime Walk):** Двумерная блуждающая траектория, направление каждого шага которой определяется последней цифрой простого числа (кроме 2 и 5, которые не дают смещения) [[76](https://blog.computationalcomplexity.org/2025/06/the-distribution-of-prime-numbers.html)]. Действующее правило (ревизия ТЗ 2, CHANGE-001): последняя цифра 1 — шаг влево (-1;0), 3 — вверх (0;+1), 7 — вправо (+1;0), 9 — вниз (0;-1); составные числа и простые 2 и 5 смещения не дают. Ось Y математическая (вверх положительна). Реализация обязана сохранять ненулевое смещение по обеим осям, чтобы трасса занимала двумерную область: вырождение рисунка в узкую горизонтальную или вертикальную полосу считается дефектом алгоритма. Этот метод генерирует сложные и запутанные траектории, которые могут проявлять скрытые закономерности в распределении последних цифр простых чисел.

4.  **Цветовая Кодировка по Модулю N:** Независимо от выбранного алгоритма (особенно Ulam Spiral), для усиления визуализации необходимо реализовать возможность окрашивания точек не только как "простые" или "составные", но и в зависимости от остатка от деления на малое целое число (N), например, от 3 до 8. Это позволит выявлять дополнительные структуры, например, какие остатки чаще встречаются у простых чисел в определенных частях спирали.

**Производительность и UX Рендеринга**

При генерации больших изображений (сотни тысяч и миллионы шагов) производительность становится критическим фактором. Чтобы интерфейс не "зависал", весь процесс расчета и отрисовки должен выполняться в фоновом потоке, не блокируя основной поток пользовательского интерфейса. Qt предоставляет для этого `QThread` или `QRunnable` с сигналами для обновления прогресса.

Рендеринг самой картинки должен быть максимально эффективным. Использование `QPainter` в Qt является оптимальным решением, поскольку он позволяет одинаковым образом рисовать на виджетах (`QWidget`) и в PDF-документах (`QPrinter`), что упрощает реализацию экспорта [[99](https://wiki.qt.io/Handling_PDF), [100](https://qt-book.com/qt6-qprinter/)]. Для очень больших изображений, которые не помещаются в память одним куском, может потребоваться реализация построчного или послайнового рендеринга, где изображение генерируется и отображается по частям.

Для улучшения восприятия скорости реакции (плавности) при прокрутке или масштабировании уже сгенерированного изображения (если это станет возможностью в будущем), следует использовать техники, снижающие "jank" (подтормаживания). Хотя для первоначальной версии это не является обязательным, стоит помнить о них: оптимизация макетов (избегание глубокой вложенности `RelativeLayout`), анимирование свойств отрисовки (альфа, трансляция) вместо свойств макета (отступы, поля), и вынос затратных операций, таких как загрузка битмапов, на фоновые потоки [[7](https://developer.android.com/topic/performance/issues/render)]. Для текущей задачи это означает, что при отрисовке сотен тысяч точек на одном кадре, `QPainter` должен быть вызван эффективно, возможно, с использованием буферизации или прямого доступа к памяти изображения, если это поддерживается выбранным backend'ом.

## Функциональные Требования: Система Персистентности и Управление Состоянием

Система персистентности является краеугольным камнем удобства использования PrimeWalker-2. Она должна обеспечивать сохранение всех важных данных пользователя между сессиями работы с приложением, включая геометрию окна, все настройки интерфейса, историю экспортов и глобальную статистику использования <Conversation History>. Это позволяет пользователю не настраивать каждый раз свои предпочтения и легко находить ранее созданные работы.

**Механизм Хранения Параметров**

Для реализации персистентности настоятельно рекомендуется использовать класс `QSettings` из фреймворка Qt [[102](https://www.pythonguis.com/faq/pyqt6-qsettings-how-to-use-qsettings/), [103](https://contingencycoder.wordpress.com/2013/04/16/restoring-qt-application-state-and-geometry-part-1/)]. Этот класс предоставляет портативный способ доступа к системным хранилищам настроек: на Windows он использует реестр, на macOS — `.plist` файлы, а на Linux — текстовые INI-файлы [[102](https://www.pythonguis.com/faq/pyqt6-qsettings-how-to-use-qsettings/)]. Это абстрагирует разработчика от платформенных различий и гарантирует, что настройки будут сохраняться в правильном месте для каждой операционной системы. При инициализации `QSettings` необходимо указать уникальные имя организации и имя приложения (например, `Bizonrelax` и `PrimeWalker-2`), чтобы избежать конфликтов с другими программами [[103](https://contingencycoder.wordpress.com/2013/04/16/restoring-qt-application-state-and-geometry-part-1/)].

Сохранение настроек должно происходить немедленно после изменения, а не только при закрытии приложения. Это защищает данные от потери в случае некорректного завершения работы (например, сбой питания или зависание системы) [[4](https://info.erdosmiller.com/blog/persistent-settings-in-desktop-applications)]. Для этого следует перехватить событие закрытия окна (`closeEvent`) и вызвать метод сохранения настроек перед тем, как закрыть окно [[101](https://www.pythonguis.com/tutorials/restore-window-geometry-pyqt/)].

**Управление Состоянием Проекта**

Помимо простого сохранения истории экспорта, программа должна поддерживать сохранение и загрузку полноценного состояния проекта. Это критически важная функция, которую запросил пользователь ("программа должна помнить ... историю изменений, чтобы мог вернуться к редактированию старых визуализаций") <Conversation History>.

*   **Формат файла проекта:** Приложение должно поддерживать экспорт состояния в файл с расширением `.pwalk`. Этот файл должен быть самодостаточным и содержать всю информацию, необходимую для воссоздания и дальнейшей работы с визуализацией.
*   **Содержимое .pwalk файла:** Файл должен быть сериализованным объектом (например, в формате JSON или YAML) и содержать как минимум следующие данные:
    *   Версию формата файла проекта (для обеспечения обратной совместимости).
    *   Все параметры генерации: `initial_number`, `step_count`, `scale`.
    *   Все параметры визуализации: `visualizer_type`, `colors` (начальный, конечный, трасса), `color_modulo`.
    *   Дата и время сохранения.
    *   Ссылка на сам файл изображения, которое было сгенерировано по этим параметрам (или само изображение, если это не слишком объемно; в большинстве случаев лучше ссылка).
*   **Процесс загрузки:** При выборе команды "Открыть проект" программа должна запрашивать файл `.pwalk`. После загрузки она должна автоматически применять все сохраненные параметры к интерфейсу (заполнять спиннеры, списки, поля цветов) и, если существует связанный файл изображения, отображать его. Это позволит пользователю немедленно приступить к редактированию и перегенерации изображения с новыми параметрами.

**Безопасность и Надежность Персистентности**

Приложение должно быть устойчиво к ошибкам при работе с настройками. При запуске оно должно проверять каждое прочитанное значение на корректность и диапазон допустимых значений. Если значение некорректно (например, размер шрифта -5), оно должно быть заменено на значение по умолчанию [[4](https://info.erdosmiller.com/blog/persistent-settings-in-desktop-applications)]. Это предотвращает ситуацию, когда невалидные настройки, сохраненные в результате ошибки предыдущей версии, вызывают сбой текущей версии программы ("краш-цикл").

Хотя в данном приложении нет явно чувствительной информации, такой как пароли или платежные данные, общие принципы безопасности следует соблюдать. Например, если в будущем появится возможность сохранять пути к файлам проектов, следует убедиться, что эти пути не используются для выполнения произвольного кода. Для защиты от несанкционированного доступа к файлу настроек (хотя это маловероятно для десктопного приложения), можно рассмотреть возможность шифрования всего файла настроек с использованием простого алгоритма, если это не усложнит разработку чрезмерно [[4](https://info.erdosmiller.com/blog/persistent-settings-in-desktop-applications)]. В текущем же случае, поскольку `QSettings` использует стандартные файлы конфигурации операционной системы, эта проблема в основном решается правами доступа к файловой системе.

## Функциональные Требования: Механизм Экспорта для Офлайн-Печати

Механизм экспорта является одним из самых сложных и важных компонентов PrimeWalker-2, так как он должен удовлетворить строгому требованию пользователя: создать файл, который можно будет беспроблемно напечатать на любом публичном терминале для печати (например, в ТЦ "Волгоградский") без необходимости дополнительных настроек или использования специализированного программного обеспечения <Conversation History>. Это требование подразумевает создание файла, который является "печатно-готовым" и, в случае большого размера, содержит все необходимые элементы для сборки многолистовой картины.

**Общие Принципы Экспорта**

Экспорт должен осуществляться в три основных формата: PDF, JPG и PNG. Для каждого формата должны быть определены строгие правила форматирования, обеспечивающие максимальную совместимость и качество вывода на бумагу. Процесс должен быть максимально автоматизирован: пользователь выбирает только выходной формат и путь для сохранения файла, а все остальные параметры (разбиение на листы, маркировка, поля) должны рассчитываться программой на основе стандартных печатных правил и размеров рисунка [[20](https://www.pdf2go.com/print-poster), [25](https://printtiler.com/guides)].

**Требования к Экспорту в PDF**

PDF является золотым стандартом для профессиональной печати, так как он объединяет все элементы (графика, шрифты, цвета) в один файл, гарантируя их консистентность [[1](https://ironmarkusa.com/bleed-crop-marks/)]. Для обеспечения максимальной совместимости с широким кругом принтеров и программ подготовки к печати, экспортируемый PDF-файл должен соответствовать строгим стандартам издательской подготовки.

| Требование | Спецификация | Обоснование |
| :--- | :--- | :--- |
| **Стандарт PDF** | PDF/X-4. | PDF/X — это подмножество PDF, специально разработанное для печати. PDF/X-4 является современным стандартом, который поддерживает живую прозрачность и цвета ICC, что обеспечивает лучшее качество по сравнению с более старыми стандартами, такими как PDF/X-1a [[10](https://img.ly/blog/what-does-print-ready-pdf-mean-understanding-pdf-x-standards-for-professional-printing/), [12](https://kapa99.com/blog/print-ready-pdf-export-settings/)]. |
| **Подгонка (Bleed)** | 3 мм (0.125 дюйма) вокруг всей площади изображения. | Подгонка — это область, которая выходит за пределы финального обреза. Она предотвращает появление белых краев из-за небольших неточностей при резке бумаги [[1](https://ironmarkusa.com/bleed-crop-marks/), [2](https://www.mailpro.org/post/what-is-bleed-in-printing/)]. Все фоны и цветные области должны доходить до края подгонки. |
| **Обрезные метки (Crop Marks)** | Метки должны быть видны на каждом листе. | Обрезные метки — это две перпендикулярные линии в каждом углу, которые точно указывают место реза. Они обязательны для тесселяции [[74](https://louisvilleeast.theprintrefinery.com/site/pdf_exporting?srsltid=AYCX9vIZw3pjwFm0e0fBBkbOSUpufYa8PIulFAo9mqvj1N0h36ZBsbDp), [75](https://cessnockprintplace.com.au/guides/how-to-supply-print-ready-pdfs/)]. |
| **Встраивание шрифтов** | Полное встраивание всех шрифтов, используемых в интерфейсе (например, в сообщениях об отчете). | Это предотвращает проблемы с отображением текста, если на принтере не установлен тот же шрифт [[10](https://img.ly/blog/what-does-print-ready-pdf-mean-understanding-pdf-x-standards-for-professional-printing/), [12](https://kapa99.com/blog/print-ready-pdf-export-settings/)]. Qt `QPrinter` поддерживает эту функцию через `setFontEmbeddingEnabled(true)` [[100](https://qt-book.com/qt6-qprinter/)]. |
| **Цветовое пространство** | Использование CMYK для цветов, отличных от основных цветов интерфейса. | Большинство коммерческих печатных процессов используют CMYK. Преобразование RGB в CMYK перед печатью гарантирует точное воспроизведение цветов [[10](https://img.ly/blog/what-does-print-ready-pdf-mean-understanding-pdf-x-standards-for-professional-printing/)]. |
| **Разрешение** | Изображение должно быть экспортировано с разрешением не менее 300 DPI для фотографического качества или 1200 DPI для линейных изображений (текст, линии) [[10](https://img.ly/blog/what-does-print-ready-pdf-mean-understanding-pdf-x-standards-for-professional-printing/)]. | Это стандартное разрешение для качественной полиграфической печати. |

**Требования к Экспорту в JPG и PNG**

Экспорт в растровые форматы (JPG, PNG) должен быть реализован аналогично экспорту в PDF, но с учетом особенностей этих форматов.

*   **Если изображение помещается на один лист A4:** Программа должна автоматически масштабировать изображение так, чтобы оно вписалось в формат A4 (210x297 мм) с небольшим отступом, и сохранить его в виде одного файла JPG или PNG. При этом должны быть добавлены обрезные метки (crop marks) на четыре угла, чтобы пользователь мог точно обрезать лист после печати.
*   **Если изображение больше одного листа A4:** В этом случае программа должна выполнить процесс тесселяции (разбиения на плитки). Результатом должен быть ZIP-архив, содержащий все страницы (плитки) в формате PNG (для сохранения качества) или JPG. Также в архиве должен быть включен файл с инструкциями по сборке, например, `assembly_instructions.pdf` или `assembly_instructions.html`, который покажет пользователю, как правильно расположить и склеить листы.

**Монтажные Метки для Многолистовой Печати**

Ключевым требованием пользователя является наличие на листах понятных отметок для сборки целой картины <Conversation History>. Эти метки должны быть автоматически сгенерированы и включены в каждый лист (плитку) при экспорте в PDF или в составе ZIP-архива.

| Тип Маркировки | Описание | Требования к Реализации |
| :--- | :--- | :--- |
| **Нумерация Листов** | Каждый лист должен иметь номер, например, "1 из 4". | Номер должен быть размещен в углу листа. Он показывает порядок печати и общее количество листов. |
| **Индикатор Ориентации** | Знак "Top" (Верх) или стрелка, указывающая на верхний край листа. | Знак должен быть достаточно крупным и видимым, чтобы пользователь мог однозначно определить, как правильно расположить лист относительно других. |
| **Контурные Метки (Registration Marks)** | Мелкие знаки (часто в виде крестиков или кругов), расположенные в углах каждой плитки, за пределами области печати. | Эти метки помогают точно совместить соседние листы при склейке, даже если есть небольшие ошибки при печати или резке. Они должны быть видны только на обрезных метках, но не на самом изображении. |
| **Направляющие для Склейки (Butt Guides)** | Линии или полосы внутри области печати, которые указывают, где нужно делать складки или наносить клей. | Эти линии могут быть представлены в виде пунктирных линий или более светлого цвета, чтобы они были заметны, но не мешали самому изображению. Рекомендуемый размер поля для склейки составляет 5-10 мм. |

Для реализации этого механизма программа должна рассчитывать сетку плиток, исходя из размеров исходного изображения и физических размеров листа А4 с учетом полей для склейки и неизвлекаемых полей принтера. Источники по онлайн-сервисам, таким как Rasterbator или Posterize PDF, предоставляют хорошую основу для алгоритма: исходное изображение масштабируется, чтобы заполнить всю площадь собранной плитки, а затем разбивается на части [[21](https://posterizer.online/rasterbator/), [26](https://oxygenpdf.com/tools/posterize-pdf)]. Каждая часть (плитка) затем рендерится с добавлением всех вышеупомянутых маркировок. Особое внимание следует уделить учету неизвлекаемых полей принтера, которые могут занимать от 3 до 10 мм с каждой стороны листа, и которые должны быть учтены при расчете рабочей области [[148](https://rasterbator.io/guides/printer-minimum-margins-borderless-printing)]. Для максимальной универсальности можно сделать размер поля для склейки настраиваемым параметром в диалоге экспорта.

## Функциональные Требования: Аналитические Инструменты и Сбор Статистики

PrimeWalker-2 должен предоставлять пользователю не только визуальные образы, но и ценную аналитическую информацию об их создании и о своей собственной работе. Этот раздел описывает два аспекта: пост-экспортный отчет, который генерируется после каждой успешной отрисовки, и глобальную статистику использования, которая собирается программой для отслеживания ее "жизни".

**Пост-Отчет об Отрисовке**

После завершения процесса генерации и отрисовки изображения программа должна автоматически отображать информационное окно с детальным отчетом. Этот отчет должен содержать точные метрики, которые пользователь может использовать для анализа характеристик своего произведения и эффективности работы программы. Все временные и ресурсные метрики должны измеряться с высокой точностью во время выполнения задачи.

| Метрика | Описание | Требования к Измерению |
| :--- | :--- | :--- |
| **Размер рисунка** | Физический размер созданного изображения в пикселях. | `(width, height)` — координаты прямоугольника, охватывающего все нарисованные элементы. |
| **Размер файла** | Общий размер экспортированного файла в мегабайтах (МБ). | Измеряется после сохранения файла в формате PNG (который не имеет потерь) или, приблизительно, для JPG. |
| **Ширина/Высота (Пиксели)** | Точные размеры изображения в пикселях. | `width` и `height` — целочисленные значения. |
| **Количество листов** | Количество листов формата А4, необходимых для печати всего рисунка. | Вычисляется на основе `Размер рисунка`, стандартного размера листа А4 (210x297 мм) и размера поля для склейки. Округляется в большую сторону. |
| **Время выполнения** | Общее время, затраченное на расчет и отрисовку. | Измеряется с помощью `QTimer` или системного таймера с точностью до миллисекунды. Включает генерацию чисел и рендеринг. |
| **Загрузка RAM** | Максимальный процент потребления оперативной памяти в течение процесса. | Измеряется путем периодического считывания значений `VmRSS` (текущий размер резидентного набора страниц) из `/proc/self/status` на Linux [[98](https://stackoverflow.com/questions/63166/how-to-determine-cpu-and-memory-consumption-from-inside-a-process)]. Результат нормализуется относительно общей доступной памяти системы. Отображается в процентах от общей свободной памяти. |
| **Количество нарисованных шагов** | Общее количество чисел, преобразованных в точки/линии. | Это значение равно параметру "Число шагов", переданному в алгоритм. |

Этот отчет должен быть структурирован и легко читаемым. Кроме того, программа должна предоставлять кнопку "Копировать отчет в буфер обмена" для удобного сохранения или отправки результатов. Важно отметить, что некоторые из этих метрик, особенно потребление RAM, могут быть сложны для точного измерения на всех платформах, поэтому для кросс-платформенной совместимости может потребоваться создание обертки вокруг системных API для получения этой информации.

**Глобальная Статистика Использования**

Помимо статистики по конкретному проекту, приложение должно собирать и хранить глобальные метрики, отражающие его общее использование. Эти данные помогут в будущем анализировать, как пользователи взаимодействуют с программой, какие алгоритмы являются наиболее популярными, и каковы характеристики наиболее часто генерируемых изображений. Сбор этой статистики должен быть анонимным, без сбора какой-либо личной информации.

Собранные глобальные метрики должны включать в себя следующее:
1.  **Дата и время первого запуска:** Фиксируется при первой же запуске программы и никогда не изменяется. Это позволяет рассчитать общую продолжительность использования продукта.
2.  **Общая длительность работы программы:** Суммарное время, в течение которого программа находилась в активном состоянии (не считая время ожидания в меню). Это значение должно увеличиваться при каждом запуске и сохраняться.
3.  **Общее количество нарисованных шагов:** Суммарное количество шагов, сгенерированных за все время использования. Это показатель "продуктивности" программы.
4.  **Самый большой размер нарисованного файла:** Отслеживается максимальный размер (в пикселях) любого изображения, созданного пользователем. Это помогает понять пределы производительности и масштабируемости приложения.
5.  **Статистика по алгоритмам:** Счетчики, отслеживающие, какой алгоритм визуализации (Ulam, Jacob's Ladder и т.д.) был выбран в каком количестве раз.
6.  **Статистика по форматам экспорта:** Счетчики, отслеживающие, в каком формате (PDF, JPG, PNG) было экспортировано наибольшее количество работ.

Эта глобальная статистика должна храниться вместе с другими постоянными настройками при помощи `QSettings` [[102](https://www.pythonguis.com/faq/pyqt6-qsettings-how-to-use-qsettings/)]. Для обеспечения анонимности, никакая информация, идентифицирующая пользователя, не должна собираться или передаваться. Для удобства разработчика и возможного анализа в будущем, в окне настроек должна быть предусмотрена кнопка "Сбросить статистику", которая позволит пользователю очистить все собранные глобальные данные .

Сбор производительностных метрик, таких как частота кадров (FPS) и время отрисовки одного кадра, является хорошей практикой, хотя и не было явно указано в первоначальном запросе. Эти данные, хотя и сложны в измерении для такого приложения, могут быть собраны с помощью `QTimer` и `QPainter::begin()` / `QPainter::end()` для анализа производительности [[7](https://developer.android.com/topic/performance/issues/render), [8](https://docs.bugsnag.com/performance/system-metrics/rendering-metrics/)]. Однако для данной версии TЗ основной упор делается на заявленные метрики.

## Нефункциональные Требования: Производительность, Безопасность и Качество

Нефункциональные требования определяют качество работы системы, ее надежность, производительность и безопасность. Для PrimeWalker-2 эти аспекты имеют решающее значение для обеспечения положительного пользовательского опыта, особенно при работе с большим объемом данных и в офлайн-режиме.

**Производительность**

Производительность — это способность системы быстро и эффективно выполнять задачи. Для PrimeWalker-2 это означает, что интерфейс должен оставаться отзывчивым даже при генерации очень больших изображений.

*   **Отзывчивость Интерфейса:** Главный поток приложения (поток пользовательского интерфейса) должен всегда оставаться свободным для обработки действий пользователя (клики, перемещение окна, изменение настроек). Любые длительные операции, такие как генерация простых чисел и отрисовка миллионов точек, должны выполняться в отдельном фоновом потоке (`QThread` или `QRunnable`). Результаты и прогресс выполнения должны передаваться обратно в главный поток через сигналы и слоты Qt. Это предотвратит зависание интерфейса и обеспечит плавную работу [[17](https://capgo.app/blog/app-state-management/)].
*   **Время Ответа:** Хотя точные цифры не указаны, цель должна быть — обеспечить время отклика на действия пользователя менее 16 мс для достижения плавной анимации в 60 кадров в секунду [[7](https://developer.android.com/topic/performance/issues/render), [8](https://docs.bugsnag.com/performance/system-metrics/rendering-metrics/)]. В контексте данной задачи это означает, что при изменении любого параметра в UI (например, масштаба или начального числа) интерфейс должен немедленно отреагировать, а фактический пересчет и перерисовка должны начаться асинхронно.
*   **Ограничение Ресурсов:** Программа должна иметь внутренние ограничения, чтобы предотвратить исчерпание системных ресурсов. Например, поле "Число шагов" должно иметь верхний предел (например, 100 000 000), чтобы избежать попыток сгенерировать изображение, которое потребовало бы гигабайты оперативной памяти или недели вычислений. При превышении предела программа должна выводить информативное сообщение, а не зависать.
*   **Оптимизация Рендеринга:** Для рендеринга больших изображений необходимо использовать наиболее эффективные методы, предоставляемые графической библиотекой (например, `QPainter` в Qt). Это может включать использование буферизированных изображений, отрисовку по частям (теггинг) или другие оптимизации, доступные для конкретного back-end. Необходимо избегать вызова дорогостоящих операций внутри цикла отрисовки миллиона точек.

**Безопасность**

Хотя PrimeWalker-2 является десктопным приложением и не работает в сети, базовые принципы безопасности все равно применимы.

*   **Защита от Ввода Некорректных Данных:** Все пользовательские вводы (в полях "Начальное число", "Число шагов", "Масштаб") должны проходить строгую валидацию. Программа не должна падать или вести себя неопределенно при вводе текста в поле для чисел или отрицательного значения для количества шагов. Вместо этого она должна показывать ошибку и отклонять некорректный ввод.
*   **Безопасность Файловых Операций:** При чтении или записи файлов (сохранение проекта, экспорт) программа должна корректно обрабатывать ошибки доступа, нехватки места на диске или попыток доступа к защищенным системным директориям. В таких случаях должны отображаться понятные сообщения об ошибках.
*   **Секретность Персистентных Данных:** Сохраняемые файлы настроек (`QSettings` обычно используют INI-файлы или регистр Windows) не являются защищенными по умолчанию. Хотя в данном приложении, скорее всего, не будет храниться критически чувствительная информация, если в будущем это изменится, следует рассмотреть шифрование этих файлов перед записью и дешифрование после чтения [[4](https://info.erdosmiller.com/blog/persistent-settings-in-desktop-applications)]. Для текущих требований достаточно правильных настроек ACL на уровне операционной системы.
*   **Уязвимости на стороне клиента:** Поскольку приложение не загружает код или данные извне, риски, связанные с XSS или инъекциями, минимальны. Основной фокус должен быть на предотвращении падений приложения из-за плохих данных.

**Качество и Надежность**

*   **Обработка Ошибок:** Приложение должно иметь централизованную систему обработки ошибок. Все неожиданные ситуации (например, сбой при выделении памяти, ошибка чтения/записи файла) должны обрабатываться с помощью конструкций `try...catch` (в C++) или аналогичных механизмов, чтобы предотвратить аварийное завершение работы. Приложение должно стремиться к "graceful degradation" — если одна часть не работает, вся программа не должна падать.
*   **Тестирование:** Для обеспечения надежности необходимо внедрить комплексное тестирование. Это включает в себя:
    *   **Юнит-тесты:** Для проверки отдельных компонентов, таких как алгоритмы генерации простых чисел и визуализации.
    *   **Интеграционные тесты:** Для проверки взаимодействия между модулями (например, работа UI с логическим слоем).
    *   **Ручное тестирование:** Для проверки пользовательских сценариев и качества интерфейса.
*   **Пользовательская Документация:** Приложение должно быть снабжено интуитивно понятной встроенной справкой (например, через меню "Помощь -> Содержание"). Также рекомендуется создать файл `README.md` в репозитории, который будет подробно описывать назначение приложения, его функциональные возможности и инструкции по сборке и запуску [[89](https://github.com/BankkRoll/repo2pdf), [91](https://github.com/James-2879/repo2pdf)].
*   **Согласованность и Пользовательский Опыт (UX):** Все элементы интерфейса должны выглядеть и вести себя единообразно. Имена переменных, комментарии в коде и стиль оформления должны следовать стандартам, принятым в проекте. Пользовательский опыт должен быть плавным: приложение должно запоминать последние открытые проекты, иметь интуитивно понятные иконки и сообщения, и не требовать от пользователя лишних действий. Например, при экспорте в PDF программа должна автоматически выбирать наилучший режим качества, а не заставлять пользователя искать нужную опцию в многоуровневом меню.

В совокупности, соблюдение этих нефункциональных требований превратит PrimeWalker-2 из простого инструмента в надежное, быстрое и качественное программное обеспечение, которое будет радовать своих пользователей своим функционалом и стабильной работой.
